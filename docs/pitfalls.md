# 踩坑与设计约束

这是从实际运行里沉淀的约束，不是理论最佳实践。每条都对应一次真实故障：要么「失败了却报成成功」，
要么「成功了但产物是错的」，要么「什么都没发生，进程挂着」。统一写 **现象 → 根因 → 做法**，
能当判据的写成判据；没实测的不写，结论都标适用边界。

读者：已跑通过一次「云盘影片 → 本地 ASR → 强制对齐 → LLM 翻译 → 回传」，现在想连续跑几百部、
不盯着也不丢产物。

## 1. 115 网盘：接口的真实行为

官方文档不覆盖这些行为，SDK 封装又会把失败包装成像权限问题的文案。目标是看报错就能判断
**凭据、信封、分片**还是**异步队列**。

### 1.1 「请重新登录」八成不是 cookie 过期

- **现象**：上传前置报 `请重新登录`（`errno 99`），与 cookie 失效文案完全一致。
- **根因**：少了注入 `user_id`/`userkey`；`upload_file_init` 回退的 `/ios/2.0/user/upload_key` 对网页 cookie 不通。
- **做法**：先 `GET https://proapi.115.com/app/uploadinfo`（`User-Agent: Mozilla/5.0 115disk/30.5.1` + cookie），
  注入这两个字段。别先换 cookie。
- **cookie 有效期不可预判**：能完成完整 OSS PUT，实测 34–37 小时，只能靠报错发现；App 接口报认证失败
  属正常。人从浏览器复制整行 `Cookie` 手工写进 `.env`——**禁止**脚本「刷新」cookie，它会覆盖写整个 `.env`，
  把还能用的那份换成失效的，不可逆。

### 1.2 秒传假成功：`upload_gettoken` 的信封锁

- **现象**：报 `115 API 请求失败`（兜底文案，像权限问题）。
- **根因**：legacy 接口 `https://uplb.115.com/3.0/gettoken.php` 返回**扁平体**（`StatusCode`/`SecurityToken`），
  没有 `state`/`data`，被信封校验判成失败。
- **为什么偶尔成功**：initupload 返回 **status=2（秒传命中）** 时直接 return，**根本不调** `_get_upload_token()`；
  只有 status=1（真传字节）才踩。所以取决于内容是否已在秒传池，不是 flaky。
- **做法**：归一化成 `{"state": True, "data": {...}}`（4 个 token 字段在顶层），实例级 patch，幂等。

### 1.3 >4.66 GiB 上传必失败：尾片声明的长度

- **现象**：`Too little data for declared Content-Length`，只能整包重传（4.92 GiB 反复传了 13 GB）。
- **根因**：`_declared_length()` 无条件返回 128 MB；文件非整数倍时尾片不足却仍声明 128 MB；分片无重试。
- **做法**：尾片按剩余实际字节声明；每分片重试 6 次（退避）；初始化/完成各 3 次。
- **验证**：尾片声明长度 == 实际字节数，满片 == 134217728。

### 1.4 下载直链只有一条路能用

| 接口 | 结果 |
|---|---|
| `download_url(pc)`（app 接口） | ❌ `errno 137 请重新登录` |
| `download_url_web(pc)` / `download_url_web2(pc)` | ❌ `errno 50028 文件大小超出限制`（2.6 GB 触发） |
| `get_download_info_from_pickcode(pc, user_agent="Mozilla/5.0 115disk/30.5.1")` | ✅ CDN 直链，`content-length` 一致 |

- **UA 必须显式传**：不传落到库默认 `115disk/37.0.2` → `HTTP 403` 反复重试（某次日志前 16 行全是 403）。
- **头字段要过滤**：返回对象是 `str` 子类，`headers` 混有 `is_115chrome` 等非字符串 → 过滤 `isinstance(v, (str, bytes))`。

### 1.5 同名文件不覆盖，会并存两份

- **实测**：同目录两次上传同名文件，两次都 `state=True`，目录里出现**两个同名文件**。
- **做法**：扫描只入队「视频在、同名 `.srt` 不在」的条目；执行遇同名**不删不改、告警跳过**。
- **理由**：旧字幕可能是人工校对过的唯一副本；要重做先人工改名或删除。

### 1.6 写操作是异步队列，失败绝不能记完成

- **现象**：`删除[某部片]操作尚未执行完成，请稍后再试！`——方括号里是**上一个**片名，
  说明服务端串行队列积压，不是 fid 传错。
- **错误处置（真实发生过）**：当「可容忍」，计数 +1 但照旧记完成 → 永不重试。
- **做法**：改名/删除失败必须重试，失败不得记完成；完成状态只能由回读核对写入。

### 1.7 上传偶发返回空 dict：只信 `state=True` 会漏传

- **现象**：偶发 `{'filesha1': '', 'filesize': -1, 'upload_id': ''}`，同分钟内下一部立刻成功。
- **做法**：上传后**重新列目录**核对名字与体积；「失败也写 done」会让该片永久缺字幕。

### 1.8 列目录的字段与缓存

- **字段**：`fs_files(...)` 是 `P115Client` 的方法；**目录条目只有 `cid` 没有 `fid`**，拿 `fid` 删目录会 `KeyError`。
- **缓存**：目录有 CDN 缓存，改名后立刻重列可能是旧结果，校验前强制刷新。
- **回收站**：端点 `webapi.115.com/rb`（**不能带尾斜杠**），字段 `file_name`/`file_size`/`id`，
  与文件列表的 `n`/`s`/`fid` 不同。
- **全盘盘点**：部分目录 `m=0`，只认 `m==1` 会漏整个分类；`ispl==1` 语义曾被写反，算出 91 vs 678；
  名字像 `xxx.HD.mp4` 的**其实是目录**。
- **做法**：只处理**指定那一个目录**。全量枚举要 510–664 次请求、40 分钟以上，期间还会用 HTTP 200
  返回风控页（非 JSON），必须把「非 200 / 非 JSON / `state=false`」都当可重试。

## 2. 音视频时钟与时间轴

时间轴错误最贵：结构校验拦不住，只会让字幕在画面上慢慢漂。

### 2.1 FFmpeg 退出码 0 不等于时长对

- **现象**：指定抽前 600 秒，退出码 0，实际 WAV 长 **653.06125 秒**。
- **根因**：取出的 PCM 时钟没对齐源容器 PTS。
- **做法**：加 `aresample=16000:async=16000:first_pts=0`；每块与整片长度都核对，**坏长度不送 ASR**。

### 2.2 段级时间必须换成词级时间 + 独立对齐

- **现象**：短句提前十几到二十多秒、跨停顿显示；旧实现把 ASR 的段级起止直接写进 SRT。
- **根因**：段级边界来自识别器窗口切分，不是词的真实发声位置。
- **做法**：词级时间 + **独立强制对齐器** + 词性/标点拆句 + 异常段回退与局部复核，最后由程序生成 cue。
- **铁律**：时间错误必须从视频重做，不能只重译，也不能全片平移——平移只是把错的变成错得更整齐。

### 2.3 同块相邻台词要联合对齐

- **现象**：同块相邻台词各自局部对齐，得到互相矛盾的开始时间（后句早于前句）。
- **做法**：对冲突台词做**一次联合对齐**，保持原词与两句身份；只对「零时长短拟声与同句台词冲突且缺独立
  定位」省略并记原因。人工确认结果与独立恢复的时钟**不被自动联合覆盖**。

### 2.4 跨块约束优先于局部定位

- **现象**：跨块短尾音局部定位越过下一块 `block.start` → 字幕**倒序**。
- **做法**：定位窗口受下一块开始约束；仍越界的低确信度片段**留痕省略**，不用重排序或平移掩盖。
- **同类**：句子与词列表分属相邻句时，仅当整块字面完全一致且句界落在词边界才重分配原词，不拆词猜时间。

### 2.5 零时长碎片有严格适用面

- **现象**：片段末尾残留一个假名，词时间为零、置信度 0.2168、恰好落在下一块起点。
- **规则**：只有「零时长 + 置信度 <0.35 + 短元音 + 声音类」可省略；正常台词、敬语前缀、正时长不套用。
- **留痕**：省略要写进 `*.alignment.json` 的 `omissions`（原文、位置、原因），否则无法区分省略与丢失。

### 2.6 验收判据要写死，并承认边界

- **硬判据**：可解析、cue>0、无空文本、时间轴单调、起止在片长内（`ffprobe` 取不到按失败）、
  中文与 `*.ja.srt` 时间轴逐条一致（`TIMELINE_TOL_MS=0`）、假名残留 = 0。
- **容差**：`CUE_TAIL_TOLERANCE=5.0s` 是尾帧延迟经验值，只管「起止是否超片长」，没逐部回归过长片。
- **CPS 是校准值**：33 份成品 / 21245 条 cue，20356 条可判中仅 3 条 >17、2 条 >25（最高 26.9）；
  889 条 <1.0s 短 cue 单列不判，故「>17 提示、>25 必看」只是提示项。
- **边界**：结构检查通过 ≠ 人工听音通过；「与原文完全相同的 cue」61 条命中多是数字、专有词。

### 2.7 完整音轨长期归档

- **做法**：完整 16 kHz 单声道 PCM 流式算 SHA1，优先同盘硬链接；`.audio.json` 绑定来源身份
  （FID、体积、SHA1、PCM 摘要），重做时核对身份才复用。源目录删掉后硬链接仍有效，但音轨不能原地覆盖、
  不能当临时缓存清。

## 3. 语音识别与强制对齐

### 3.1 过滤阈值过严会静默丢对白

- **现象**：字幕条数偏少，轻声、气声、短促对白整段消失，**没有任何报错**。
- **根因**：默认阈值按「普通影视对白」调（`no-speech 0.7 / logprob -1.0 / 短句 -2.5`）。
- **做法**：口语化、多轻声的片源固定
  `--no-speech-threshold 0.95 --min-logprob -2.0 --min-logprob-short -4.0 --keep-duplicates`。
- **同类**：`--language auto` 会在片段间跳变导致时间轴漂移或整段译错，片源语言固定就写死（`--language ja`）。

### 3.2 空字幕要判成音频异常，不能当完成

- **现象**：提取「成功」但产物不足 100 B。
- **做法**：判音频异常 → 记 `skipped_empty_srt`、删本地视频、**不算完成**、不进翻译。
- **配套**：0 字节残留 `.srt` 会被误判成「已有字幕」，提取前先清。

### 3.3 单部失败不能把条目弄丢

- **现象**：历史实现失败后 `continue`，任务从队列消失，同一部再也不重试。
- **做法**：失败只记状态（`skipped_extract_failed`），条目保留，重跑会重试。
- **证据**：有过 `rc=2` 首次失败、重跑即成功的案例；`rc=4294967295` 重试 3 次后跳过并记状态。

### 3.4 识别与对齐的环境不是 `uv sync` 能重建的

- **根因**：GPU 模型、独立对齐环境、CUDA 库目录都是手工放置，不在依赖清单里。
- **做法**：路径集中在一个配置模块里；清理时不删未知文件，不重复试全部候选模型。

### 3.5 复用译文的判据是「文字 + 时间轴哈希」

- **坑**：只看文件名一致就复用 → 同名不同内容/时间时错配。
- **做法**：日文文字与时间轴哈希完全一致、中日配对验收通过才复用；缓存绑定音轨摘要与原始识别摘要。
- **候选 ≠ 已验证**：编号、片长只用于排队；分段或音轨不一致的版本不得套用整份字幕。

### 3.6 轻声不等于非语言发声

- **做法**：普通分歧保留原文、只写独立疑点；确实低确信度的文字才省略并留原因。
- **禁止**：把台词自动改写成「非语言声音」——危险默认值，已停用。

## 4. 翻译：提示词与验收判据

### 4.1 默认提示词被覆盖 → 151 处占位标记

- **现象**：17 部产出里共 **151 处**「[原文待核]」。
- **根因**：共享默认提示词被另一条流水线的严格 QA 协议覆盖，而那批脚本没显式传 `--system-prompt`。
- **做法**：调用方一律显式传提示词；默认回退文件不许当风格编辑入口。
- **检查要查对文件**：扫整个 prompts 目录的检查在结构变化后永远返回空，只给虚假安全感。
- **缺口**：至今没有测试断言「批处理必须显式传某个提示词」。

### 4.2 提示词与解析代码是两处独立演化，中间会静默丢数据

- **现象**：每批都生成全局上下文，模型确实输出了术语表，但术语一致性毫无改善；日志「术语: 0 条」是唯一线索。
- **根因**：生成端要求 `"terms"`，渲染端读 `"verbs"`/`"glossary"`——键名不匹配，术语表 100% 被丢弃且不报错。
- **做法**：按 `terms` →（兼容历史缓存）`glossary` → `verbs` 读取，日志打印真实条数；改任一侧都端到端跑一次。

### 4.3 解析层要「拒绝」，不能「填补」

- **最严重的事故**：模型漏行或重编号时，旧代码按顺序**填补**缺失 ID → **译文整段前移一位**，全片错位。
- **正确行为**：缺行、重复 ID、空译文、无编号、多余条目——一律抛错，不产出文件。
- **配套坑**：编号正则不认全角冒号，`7：你好` 落进「无编号」分支；整片模式不许自带更宽松的解析。
- **代价可接受**：宁可整批失败重跑，也不产出静默污染的字幕。

### 4.4 逐句缓存会被投毒，对影片对白禁用

- **现象**：被污染的旧译文被逐句缓存命中并写回，错误跨多次运行传播。
- **做法**：影片对白不查也不写逐句缓存（条目全进 `pending`），缓存文件不再创建。
- **作废**：旧文档「重复跑提速 5–10 倍」不成立，能提速的只有断点续传与全局上下文缓存。

### 4.5 失败不得把原文当译文落盘

- **现象**：并行批次超时后仍走到写盘逻辑，产出「日语内容的中文字幕」。
- **根因**：`future.result(timeout=360)` 写死，`--timeout` 调大也无效。
- **做法**：失败即整体失败、不产出文件；超时跟随 `--timeout`（另留 60 秒缓冲）。

### 4.6 假名残留检查只是结构检查

- **做法**：`looks_untranslated()` 命中就抛错、不产出文件，并对疑似条目拆单条重试 2 次。
- **边界**：审校只能显式开 `--llm-review`；旧文档的「同句取多数票统一」已不在代码里，
  `--no-review` 是空开关。

### 4.7 模型 ID 与 URL 决定走哪条通道

- **事实**：`api.deepseek.com` 只接受 `deepseek-flash` 与 `deepseek-v4-pro`；写 `deepseek-v4.1-flash`
  返回 **400**，写 `deepseek-chat` 能跑但被网关分流到不同后端（自报 v3.2）。
- **通道判断是字符串匹配**：URL 含 `deepseek`/`openai` 才走 `/chat/completions`，否则当本地 Ollama。
- **做法**：固定 `--model deepseek-flash --url https://api.deepseek.com`；key 顺序 `DEEPSEEK_API_KEY` →
  `OPENAI_API_KEY` → `.env`。

### 4.8 上下文只带相邻原文，思考模式单独记账

- **上下文**：每批只带前 `--context-lines`（默认 100）条**原文**，不传播旧中文。
- **思考模式**：API 默认开思考，漏参数会产生大量 reasoning token（实测两长片分别占输出 88.1%/89.4%）；
  总等待耗时不能当推理时间；禁用思考的断点不得混入正式译文。
- **优惠时段**：`--off-peak-only` 要**逐请求**守门（含重试与审阅），提前 `timeout+60` 秒停发。

## 5. 并发与断点续跑

### 5.1 收尾不能用「数 sentinel 条数」

同一 bug 一天内被踩四次，前三种修法都对、又都不彻底（第四种见下文「最终方案」）：

| 修法 | 实测 | 为什么不行 |
|---|---|---|
| 共享计数判断谁是最后一个 worker | 永久阻塞在 `q.get()` | 计数与投递有竞态 |
| 每个退出的线程投 1 个 `None` | 上游 1、下游 3 → 只放走 1 个 | 上游线程数 < 下游时不够 |
| 每线程投「下游线程数」个 `None` | 终止符把 2 线程的上传池**提前收掉** | 终止符跑到未处理条目**之前**，静默漏上传 |

- **最终方案**：计数式屏障——worker 在 `finally` 里累加完成数，达到总数且尚未关闭的**那一次**（且仅一次）
  才向下游投「下游线程数」个 `None`；触发条件是计数，不是「某个线程碰巧最后退出」。
- **验证**：条目 1/3/7 → 实际上传 1/1、3/3、7/7（修复前 0/1、2/3）；改并发只需改常量。
- **失败也要转发**：失败条目必须向下游转发跳过标记，否则屏障永远收不了口。

### 5.2 看门狗要轮询，且只在工作屏障关闭后计时

- **现象**：日志说「某级线程未退出，补 sentinel」，而那些线程早已退出。
- **根因**：`if any(alive): rescue(); t.join(timeout=…)`——`alive` 在 `join` 之前检查，对已退出线程误报。
- **做法**：轮询 `is_alive()`，真卡住超阈值（1800/1800/900/600 秒）才补；最终手段是 dump 线程栈 + 强制退出。
- **关键**：不能按**进程总时长**杀——等优惠、正常工作都会被当成卡死。

### 5.3 节流等待必须短轮询

- **现象**：只剩最后几个条目时无谓多耗 10–20 秒。
- **根因**：等水位时 `stop_event.wait(10)` 睡下去，睡着后不再检查队列是否已空。
- **做法**：间隔 0.5s（磁盘紧张 30s）；实测 7 条目 20.0s → 1.0s。

### 5.4 四段必须独立并行，不能两两合并

- **现象**：初版把「下载+提取」「翻译+回传」各自串行 → 翻译在等、提取没提前。
- **做法**：下载 3 ∥ 提取 1 ∥ 翻译 3 ∥ 回传 2，各段水位 3；提取受显存限制必须串行。
- **验证**：写「实际重叠」测试断言 A 识别时 B 已下载；只看线程数不算验证。

### 5.5 状态文件与断点

- **key 必须是字符串**：tuple 作 key 经 JSON 往返会变字符串，导致查不到。
- **幂等**：`uploaded` 跳过；本地已有视频不重下；已有 `.zh-cn.srt` 不重翻。
- **checkpoint**：原子保存乱序完成条目 + 连续前缀，失败后只补缺项；手工改状态 JSON 会产生假状态。

### 5.6 改代码后必须重启进程才生效

- **现象**：日志与源码「矛盾」——一个进程按旧逻辑传云端、另一个按新逻辑写本地。
- **根因**：Python 启动时加载源码，改文件不影响已在跑的进程。
- **做法**：对比源码 mtime 与进程启动时间（`Get-CimInstance Win32_Process`）；启动时打印运行时指纹。

### 5.7 墙钟超时会把「等优惠」误判成失败

- **根因**：线程里在等时段，外层 `Future.result(timeout+60)` 按墙钟 360 秒误超时。
- **做法**：优惠模式下批次不设墙钟截止，HTTP 各保留 300 秒超时；重启只针对本批并复用 checkpoint。
- **禁忌**：别把空超时误判成 API 拒绝后盲目重发。

### 5.8 云端并发上限不能套用本地显存结论

- **事实**：单文件多路请求能提高吞吐；官方限流给出 `deepseek-flash` 每账户 2500 路，本地 Ollama 仍建议 1 路。
- **做法**：单文件 8 路 × 最多 80 文件，按「最先完成」补位。

## 6. 文件校验与回传事务

这章是「会永久丢东西」的地方，顺序都不是风格问题。

### 6.1 验收四步，顺序不可换

1. 原文归档到本地并通过 **sha1 + 体积**校验；
2. 字幕结构验收通过（可解析、cue>0、无空文本、时间轴单调、起止在片长内、中日时间轴逐条一致）；
3. 上传接口返回成功；
4. 云端**体积**一致（返回 `sha` 时再比 sha1）。

- **任一步没过**：只记状态与日志，**本地文件全部保留**、不上传、不清理。
- **历史缺口**：早期实现在归档返回 `None` 时**仍继续上传并删本地**，等于丢掉原文唯一副本。

### 6.2 「上传成功即删」是错的，正确触发是「验收通过才删」

- **三分**：上传完成、验收通过、观看效果合格是三件不同的事，状态字段不能混写。
- **`uploaded` 的含义**：上传 + 验收通过 + 本地已清理，并记录 `cues`/`bytes`/`sha1`/`verify`。

### 6.3 归档的「同名」要按内容判定

- **旧口径**：同名且大小相同就跳过 → 体积相同但内容不同时漏检。
- **新口径**：sha1 + 体积都一致才复用；内容不同则旧版改名 `.prev`，复制走 `.part` 临时件，
  失败只删临时件。
- **命名坑**：`with_suffix(".ja.srt.prev")` 会得到 `X.ja.ja.srt.prev`，要用 `with_name(name + ".prev")`。

### 6.4 暂存名必须是 `.srt` 结尾，改名会返回「假成功」

- **根因**：115 批量改名**保留旧扩展名**（`.srt.mvplus-stage-…` 不是 SRT 扩展名）；用字典列表调
  `fs_rename` 会展开出错误 FID，库支持的是 `(fid, name)` 元组。
- **做法**：暂存用 `<stem>.mvplus-stage-<原fid>.srt`；改名用元组并补真实格式回归。
- **收尾**：以「名字/FID/体积/SHA1 回读」为准，不只信 `state`；只清理本任务生成且 SHA1 一致的错误副本。

### 6.5 发布同名冲突：不动视频名，旧字幕留痕

- **规则**：新字幕用**当前视频的真实 stem**；旧字幕与占位旧版分别加「旧」，仍以「旧.srt」结尾。
- **纪律**：不删除云端旧字幕，流程逐步落盘事务日志（临时名上传 + SHA1 核对 → 旧字幕加旧 → 改同名 → 再核对）。

### 6.6 下载完整性先校验，再交给下游

- **现象**：`Invalid data found when processing input`；旧代码据此误判音频问题并删掉还能救的视频。
- **做法**：下载后按远端大小做 0.99 比例校验 + `ffprobe` 探时长；提取前清 0 字节残留。
- **退化坑**：远端 `size` 缺失时 `0 > 0*0.95` 恒假 → 永远重试，比例校验须在 `size` 非空时启用。
- **并发坑**：115 对并发连接敏感（`peer closed connection…`），下载并发固定 3，不要用 4–5。

### 6.7 磁盘水位与本地清理

- **规则**：水位 = 单部大小 × 1.5，下载前检查；可用空间低于 30 GB 暂停取新任务。
- **实测教训**：「在途囤货 + 未及时删本地」曾把 80 GB 限额冲到 106 GB；加在途上限 + 验收后清理才跑完 165 GB 批量。
- **判读**：`uploaded` 但本地文件还在 → 清理异常；非 `uploaded` 的保留是设计，重跑会继续。

## 7. GPU、显存与运行环境

### 7.1 cuBLAS/cuDNN：改 `PATH` 没有用

- **现象**：`--cuda` 提取 `rc=2`，栈底 `Library cublas64_12.dll is not found or cannot be loaded`，GPU 利用率 0%。
- **两个根因**：① 拼 DLL 目录时**多拼一层 `nvidia`**；② Python 3.8+ 起 Windows 的 DLL 搜索**不再看 `PATH`**。
- **做法**：遍历 `lib/cuda/nvidia/*/bin` 与 venv 的 nvidia 包目录，逐个 `os.add_dll_directory()` 并打印结果。
- **教训**：目录是从旧环境搬来的，旧布局恰好命中，搬完没回归；另一入口脚本只改 `PATH` 且绕过 `main()`，
  主修复对它不生效。
- **显存**：`large-v3-turbo` 约占 2.6 GB，12 GB 卡安全；**并发 2 份不会更快且易 OOM**
  （12 GB/31 GiB 机器实测），更大显存未验证。

### 7.2 路径、外部进程与「卡死」判读

- **路径**：外部工具在含中文或空格的路径下会报错退出 → 纯 ASCII 路径，参数一律加引号。
- **PIPE 死锁**：外部工具进度条写 stderr 撑爆管道会互相等死 → 重定向到文件或加 `--no-progress`。
- **判读卡死**：CPU 增量 + 缺页 + 内存三维度一起看，不要只看文件大小（打开中的文件不更新体积）。

### 7.3 编码：乱码和「写坏文件」是两件事

- **显示乱码**：控制台代码页不是 UTF-8，只是显示问题，不要据此判断文件坏了；用编辑器看 `run.log`。
- **真写坏**：`Get-Content | Set-Content` 全文件替换时 PowerShell 默认按系统 ANSI 读写，UTF-8 中文
  被不可逆破坏（曾把注释写坏）。
- **纪律**：改文本只用编辑工具；脚本内 `sys.stdout.reconfigure(encoding="utf-8")`。

### 7.4 凭据卫生与取证习惯

- **真实事故**：`.env.bak` 被写进 `.git` 对象库，含**真实 cookie 明文**；不在任何 commit 里，
  `git log` 看不到，但 `git cat-file -p` 能取出来，`git bundle` 也会带上。
- **纪律**：`.env` 进 `.gitignore`；不要留 `.env.bak`；清理悬空对象会永久丢历史，先确认不需要取证，
  处置同时轮换凭据；子进程不继承 cookie。
- **取证**：`faulthandler.dump_traceback_later(25)` 定时打所有线程栈；取指定线程栈用
  `sys._current_frames()`。先取证再改代码。
